# Team work

## Pair programming 

As stated in [work-practices](work-practices.md#pair-programming), pair programming has been used a core principle
where it is applicable. The members of the group have different experience and expertise, and through working together
the group has been able to teach each other new concepts. 

The group has also been able to come up with better solutions as a result of pair programming.
An example of this has been the largely improved login page UI as a result of working together. 
This was done through combining different group members' experience as some are more experienced with
backend work, and others are more experienced with frontend work. 

All code that is to be pushed to main is to be merged through pull requests as a general rule.
This gives the group the ability to review all code, which has lead to multiple bugs being
discovered before merging to main. We have had success with this approach. 

## Meetings 

The group decided early on to meet at a specified time every single week, and so far it has
taken place every week without fail. During these meetings we discuss the current state of the project, 
the issues that are open and lastly what should be completed by next week. 

This gives us a structured way to keep track of the project and what parts of the project
the different members are working on. So far it has worked well, and we have been able to 
coordinate the completion of different parts together. For example, we have been able to coordinate
the UI with the persistence functionality, making sure that the core logic works and building around that. 

While these meetings do help us keep up to date and aligned, informal discussions occasionally cause us to become 
sidetracked. This is something we can improve upon by having brief pre-meeting agendas to make
sure we stay on track for the entire meeting. 


## Issue management through GitHub project

Since the beginning of the project the group has used a project on GitHub to track the progress
on the different releases. This has mainly been done through issue tracking. This has worked well 
as we have been able to assign different members to different parts of the project. This has also 
lead to us having to reflect about what type of issues we open, which further leads to reflection of
how functionality is implemented within the project.

However, we have also had certain problems with issues. When we first began using issues we created
issues that were too large, and were not descriptive enough of the problem at hand. This is something
we have started resolving by using sub-issues within these larger issues.
