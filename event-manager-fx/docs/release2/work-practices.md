# Work practices

## Architecture

We discuss issues and features that will affect the project's architecture before implementing, to reach a consensus on the architecture so everyone can work with an up-to-date mental model of the project.

## Issues

An issue should describe the task and intended end state clearly enough that the assignee can complete it without having to make assumptions about the requirements or expected result. Larger tasks are divided into multiple issues when appropriate. We thus try to keep issues small and manageable, so as to minimize assumptions on the assignee's part.

## Branches

Changes are not made directly to `main` for normal development work. Development is always done in branches, normally with one branch per issue, depending on sub-issues and the like.

## Pair programming

We use pair programming in the project, although it is not used arbitrarily for every single development task. We apply pair programming particularly when fields of expertise differ between group members, and each member stands to learn from it.

## Testing

We strive to write functionality tests while developing features, so the testing can serve as somewhat of a guide.
